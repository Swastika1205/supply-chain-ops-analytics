# Supply Chain & Operations Performance Analytics

## Executive Problem

**Which carriers, regions and operational bottlenecks are driving SLA breaches, delivery delays and avoidable operational cost — and where should management intervene first?**

This consulting-style analytics case study uses **7,865 synthetic shipments** across 6 fictional carriers and 4 regions to diagnose service-level performance and prioritize operational interventions.

> **Data note:** all shipment data and business figures are synthetic, generated by `scripts/generate_data.py`. No real company or carrier performance is represented.

## Executive Insights

From the synthetic dataset, management can investigate:
- SLA breach rate by carrier, region and tier
- Delay hotspots and recurring root causes
- Carrier-level service/cost trade-offs
- Estimated delay-related cost exposure
- High-priority bottlenecks for intervention

The project intentionally avoids claiming real-world savings. Any impact estimate must be presented as a scenario/assumption-based calculation.

## Consulting Workflow

**Business question → KPI definition → data quality → SLA diagnosis → bottleneck/root-cause analysis → cost impact → intervention priority → executive dashboard**

## Data Generation & Methodology (read this before an interview)

Earlier versions of this dataset shipped `cost_per_day_delay` and `estimated_delay_cost` as pre-existing CSV columns with no code showing how they were produced — and, on inspection, the two columns weren't even consistent with each other (`estimated_delay_cost` didn't equal `delay_days × cost_per_day_delay` for the same row). That's fixed:

- **`cost_per_day_delay`** — computed by `src/cost_model.calculate_cost_per_day_delay()`: a fixed daily handling surcharge plus a small value-based daily rate on the shipment's declared value. The exact coefficients are documented in that file and explicitly flagged as illustrative, not calibrated against real carrier penalty clauses.
- **`estimated_delay_cost`** — `delay_days × cost_per_day_delay`, computed by `src/cost_model.calculate_estimated_delay_cost()`. Zero for on-time shipments by construction.
- **Carrier performance spread** — each carrier has a documented on-time-probability and delay-severity bias in `scripts/generate_data.py` (`CARRIER_PROFILES`), so the SLA breach differences you see across carriers are a deliberate, disclosed generation choice, not incidental noise.

**Validated, not just asserted:** `tests/test_data_consistency.py` checks that (a) the shipped `cost_per_day_delay` matches recomputing it from `shipment_value`, (b) the shipped `estimated_delay_cost` matches recomputing it from `cost_per_day_delay × delay_days`, (c) on-time shipments always show zero delay cost, and (d) there is a genuine, non-trivial spread in SLA breach rate across carriers (not just noise).

To regenerate the dataset (e.g. after changing the cost model or carrier profiles):
```bash
python scripts/generate_data.py --rows 7865 --seed 7
```

## SQL

`sql/operations_kpis.sql` includes flat aggregate views (KPIs overall, by carrier, by region/delay-reason, by tier) and two window-function queries: a `LAG() OVER (PARTITION BY carrier ORDER BY month)` query for month-over-month change in SLA breach rate, and a `RANK() OVER (PARTITION BY region ...)` query for the top-3 worst carriers within each region. Both were executed against the actual dataset (via SQLite) to confirm they run correctly, not just written to look plausible.

## Design Decisions

- **The delay-cost formula and carrier performance biases are hand-set and documented, not fitted to real outcomes.** This is stated plainly (see Data Generation & Methodology) rather than implied to be more rigorous than it is.
- **`priority_score` weights (50% SLA breach rate / 30% relative delay severity / 20% relative delay cost) are also hand-set.** In a real engagement these would be calibrated against actual intervention outcomes or stakeholder input, not assumed.

## Limitations

- Synthetic portfolio data; carrier names, performance biases, and cost coefficients are illustrative, not calibrated against real carrier contracts.
- `priority_score` and the underlying cost model use explicit, documented assumptions rather than fitted/validated parameters.
- Recommendations are analytical priorities, not operational commitments.

## Reproducibility Notes

- Test modules use in-memory DataFrames, so the test suite does not depend on the caller's working directory.
- The walkthrough resolves the project root before loading `data/supply_chain_performance.csv`.
- Command-line modules resolve the dataset relative to their own source file.
- `requirements.txt` covers the runtime imports used by the project and notebook (`pandas`, `numpy`, `matplotlib`, `pytest`, `jupyter`).
- Prioritization logic is covered by `tests/test_prioritization.py`; data/code consistency is covered by `tests/test_data_consistency.py`.
